## 4. データベース

### data/survey.db（人が入力したもの・消すな）

| テーブル | 内容 |
|---|---|
| `sites` | オルソ1枚ぶんの範囲・ズーム・タイル形式 |
| `trees` | 候補木。検出結果と現地調査結果の両方 |
| `photos` | 現地写真（実体は `data/photos/`） |
| `history` | 誰がいつ何を変えたか |

`trees` の列は2種類に分かれる。

- **検出由来**（取り込み直すと更新される）
  `lon, lat, x, y, elev, canopy_h, rinpan, kosyoban, chiku, sp_main, nara_rank, chiban, area_m2, score, priority`
- **人が入力**（取り込み直しても**絶対に触らない**）
  `status, survey_date, surveyor, species, dbh_cm, leaf_color, dieback, boring, frass, stand, misjudge_reason, access_note, treatment, treatment_date, memo`

この境界は `tools/db.py` の `SURVEY_FIELDS` と、
`server.py` の `EDITABLE` で定義している。列を足すときは両方に足すこと。

ステータスの内部コードは
`unsurveyed / damaged / clean / pending / unreachable / treated`。
表示名と色は `tools/db.py` の `STATUS` にまとめてある。ここを直せば画面も凡例も追随する。

### data/forest.db（再生成可）

| テーブル | 内容 |
|---|---|
| `rinpan` | 森町の林班界（165件）。ジオメトリはGeoJSON文字列 |
| `kosyoban` | 森町の小班（10,301件）＋森林調査簿の属性 |
| `meta` | 出典・座標系・統計 |

`nara_rank` は 2=ナラ類確実（樹種62/63/64）、1=可能性（98/99）、0=該当なし。

## 6. よくある改修

### ステータスを増やす／名前を変える

`tools/db.py` の `STATUS` を編集するだけ。画面の凡例・フィルタ・詳細ボタン・
CSVの日本語表記まで、すべてここを参照している。

### 検出をAIモデルに差し替える

`tools/detect.py` の `detect_candidates(ortho, params, progress)` を差し替える。
戻り値は dict のリストで、最低限これらのキーがあればよい。

```python
{'x': 平面直角XI系の東距, 'y': 北距, 'area_m2': 面積, 'score': 0..1}
```

`ortho` は `tools/ortho.py` の `Ortho` で、`ortho.rgb`（H×W×3 uint8）、
`ortho.alpha`（H×W uint8）、`ortho.sx`（画素の地上寸法m）、
`ortho.pixel_to_xy(col,row)` が使える。

優先度の決め方を変えたいときは同じファイルの `priority_of()` を直す。

### 対象を森町以外の市町村に変える

`tools/build_forest.py` の先頭で

```python
SHINKOKYOKU = '01'   # 渡島
MORI = '15'          # 森町
ZIP_URL = 'https://www.fics.pref.hokkaido.lg.jp/FILE/2024/GIS/01oshima.zip'
```

を変える。市町村コードは `data/_src/oshima/森林調査簿コード.xlsx` の
「市町村コード」シートにある（振興局コード＋市町村コードの組）。
他の振興局は URL の `01oshima` を `02hiyama` などに変える。

`tools/fetch_basemap.py` の `MORI_BBOX` も対象範囲に合わせること。

### 森林データを最新年度に更新する

北海道は毎年オープンデータを更新している。
`ZIP_URL` の年（`FILE/2024/`）を新しい年に変え、
`data/_src/01oshima.zip` を消してから `初期設定.bat` を実行すればよい。
**`forest.db` は作り直されるが、`survey.db` は触られない。**

ただし林班・小班の区画が変わった場合、既存の候補木の `rinpan`/`kosyoban` は
古いままになる。付け直したいときはオルソを再取り込みする。

### タイルの形式を変える

既定は WebP（Pillow が対応していれば）。対応していなければ PNG に落ちる。
`--tile-format png` で強制できる。
サイトごとの拡張子は `sites.tile_ext` に記録され、画面はそれを見てURLを組み立てる。

## 7. 検算・動作確認

```bash
# 投影計算が正しいか（引き継ぎ資料の実測値と照合）
py -3 tools/geo.py

# オルソを読めるか・どこに落ちるか（DBには書かない）
py -3 tools/ingest_ortho.py "オルソ投入/siteA_ortho.tif" --dry-run

# サイト一覧
py -3 tools/remove_site.py

# サーバーだけ起動（ブラウザを開かない）
py -3 server.py --no-browser -v

# 座標の計算が正しいか（国土地理院の公式サービスと突き合わせ）
py -3 tools/verify_coords.py
py -3 tools/verify_coords.py 42.105986 140.683474   # 1地点だけ
py -3 tools/verify_coords.py --offline              # 通信なしの分だけ

# オルソの絶対位置が何mずれているか（新しいオルソを入れたら必ず一度）
py -3 tools/check_ortho_shift.py
py -3 tools/check_ortho_shift.py siteB -v      # 窓ごとの結果も見る
```

### オルソのずれの測り方（tools/check_ortho_shift.py）

ドローンのオルソは形と距離は正確でも、地球上のどこにあるかが数メートルずれる。
その量を数字で出すのがこの道具。やっていることは

1. 取り込み済みのオルソタイル（z18）を 4×4 枚つないで約450m四方にする
2. 同じ範囲の国土地理院「シームレス空中写真」を取ってきて同じ大きさにする
3. 二つを **位相相関**（FFT）にかけ、模様が一番よく重なるずらし量を求める
   （放物線あてはめで画素より細かく。z18 の1画素は約0.44m）
4. 相関の山の際立ち（SNR）が 8 未満の窓は捨て、残りの中央値をとる

窓ごとの結果がそろっていれば、それは平行移動のずれ。バラバラなら測れていない。
一面の森林だと照合できる模様が無く「測れませんでした」になる。**ずれが無いという
意味ではない。**

2026-09-07 時点の結果は `docs/位置合わせと精度.md` に表で残してある
（Site F・G はほぼぴったり、Site B は約7m、Site H は約3.6m、A/C/D/E は測定不能）。

比べる相手のシームレス空中写真自体にも数メートルの誤差と撮影時期の差があるので、
出てくる数字には ±2m ほどの幅がある。GCPやRTKを使わずに絶対精度を上げる方法は
無いので、この道具は「どれくらい信用してよいか」を知るためのもの。

なお `data/tiles/` には過去の試作の残り（`siteA_probe` など）が入っているので、
既定では `survey.db` の `sites` に登録されているものだけを見る。

## 8. 既知の制約

- **森林調査簿は民有林のみ。** 国有林は小班に入らないため、
  そこにある候補は「民有林の小班の外」として優先度が下がる。消してはいない。
- **オルソの絶対位置に水平±3〜5mの誤差。** GCP・RTK未使用。仕様。
  境界確定・図面作成には使えない。画面にも常時表示している。
  実測ではサイトごとに差が大きく、Site F・G は約1m以内、Site B は約7m、
  Site H は約3.6m ずれていた（`tools/check_ortho_shift.py`、
  結果は `docs/位置合わせと精度.md`）。
  **オルソを見て決めた木の座標には、そのサイトのずれがそのまま乗る。**
- **樹高は参考値。** ドローンDSM − 国土地理院DEM。DSMの高さが気圧高度由来のため
  誤差が大きい。サイトごとに下位5%を地面とみなす簡易補正を入れてあるが、目安。
- **ログイン機能は無い。** 単独PC・庁内LAN前提。
  `--host 0.0.0.0` で外に開くときは、信頼できるネットワーク内に限ること。
- **年次比較の画面は未実装。** サイトを年ごとに分けて登録することはできる。
- **点群（LAS）は扱っていない。** Web で見せるなら PotreeConverter か
  py3dtiles を挟む必要がある（元の引き継ぎ資料 3-4 参照）。

## 10. 追加した機能（画面まわり）

### API

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/api/locate?lon=&lat=` | 1点の平面直角座標・林班・小班・樹種・標高を引く |

| POST | `/api/import/cancel` | 取り込みを中止 |

取り込みは `server.py` の `ImportJob` が `tools/ingest_ortho.py` を
`subprocess` で起動し、標準出力を1行ずつ拾って画面に返す。
生ログは `data/_import.log` にも残る（失敗時の調査用）。

### 位置の編集

`POST /api/tree/<id>` に `lon`/`lat` を渡すと、サーバー側で
平面直角座標・林班・小班・樹種・代表地番・標高を引き直す
（`locate_point()`）。変更履歴には「位置」としてまとめて1行だけ残す。

### 画面の道具

`app/app.js` の `setMode()` が `add` / `measure` の状態を持つ。
地図のクリックは `onMapClick()` が状態に応じて振り分ける。
現在地は `navigator.geolocation`（HTTPSでなくても `127.0.0.1` は安全な文脈として
扱われるため動く）。座標のパースは `parseCoord()` が
10進・度分秒・平面直角XI系の3通りを受ける。
平面直角→緯度経度は逆変換を持たないので、`/api/locate` を数回叩いて
反復で寄せている（6回で 5cm 以内に収束する）。

### 背景地図のフォールバック

`FallbackTile`（`L.TileLayer` の派生）が、ローカルの
`data/basemap/...` を先に読み、404 なら地理院タイルへ切り替える。
現地（圏外）では取り込み済みの範囲が、事務所ではその外も見える。
コンソールに 404 が出るのは仕様。

## 11. 座標系まわり（衛星画像対応）

`tools/geo.py` の `TransverseMercator` クラスが横メルカトルを一般化して持つ。
平面直角座標系もUTMも同じクラスで表せる（違うのはパラメータだけ）。

```python
geo.jp_plane(11)   # 平面直角座標系11系（lat0=44, lon0=140.25, k0=0.9999）
geo.utm(54)        # UTM 54N（lat0=0, lon0=141, k0=0.9996, FE=500000）
geo.XI             # 本業務の既定（= jp_plane(11)）
```

`tools/crs.py` が画像の座標系を見分ける。

| 関数 | 役割 |
|---|---|
| `crs.detect(path)` | GeoTIFFのGeoKey → `.prj` の順に見て座標系を返す |
| `crs.from_epsg(code)` | EPSGコードから作る |
| `crs.from_wkt(wkt)` | `.prj` の WKT から作る |

対応しているEPSG: 平面直角(6669-6687 / 2443-2461 / 30161-30179)、
UTM(32601-32660 / 32701-32760 / 6688-6695 / 3097-3101)、
地理座標(4326/4612/6668)、Webメルカトル(3857)。

`Ortho` は `self.crs` を持ち、タイル生成の制御格子で `crs.from_lonlat()` を呼ぶ。
座標系が違っても同じ経路で処理される。`--epsg` で明示指定もできる。

新しい投影法（ランベルトなど）を足すなら、
`to_lonlat` / `from_lonlat` を持つクラスを作って `crs.from_epsg` に足すだけでよい。

## 12. 追加したAPI

| メソッド | パス | 用途 |
|---|---|---|
| POST | `/api/trees/bulk` | まとめて更新。`{ids:[], fields:{}, _who}`。履歴は1件ずつ残る |
| POST | `/api/photos/import` | 現地写真をまとめて取り込み、EXIFのGPSで木に紐づける |

`/api/photos/import` は multipart。フィールドは
`radius`（何m以内を同じ木とみなすか）、`create`（近くに無いとき登録するか）、
`site`、`status`、`_who`。戻り値は
`{attached, created, nogps, skipped, summary}`。

EXIFの読み取りは `tools/exif.py`。**Pillow を使わず標準ライブラリだけ**で
JPEGのAPP1からTIFF構造をたどり、GPS IFD（タグ34853）を読む。
ビューアー本体の「標準ライブラリのみ」を保つため。

`server.py` の `point_elevation()` も同じ理由で、numpy を使わずに
`.npy` のヘッダ長を読んで目的の1画素へ直接シークしている。

## 13. 見比べ（スワイプ）の実装

Leaflet の **pane** を2つ作り（`cmpL` / `cmpR`）、それぞれにタイルレイヤーを入れて、
pane の `clip-path: inset(...)` を動かしているだけ。
タイルは既存のものをそのまま使うので、容量も描画負荷も増えない。

```js
pane('cmpL').style.clipPath = `inset(0 ${w - px}px 0 0)`
pane('cmpR').style.clipPath = `inset(0 0 0 ${px}px)`
```

## 14. 位置の微調整

`trees` に3列を後から足してある（`tools/db.py` の `MIGRATIONS` が
既存の survey.db にも自動で `ALTER TABLE` する）。

| 列 | 意味 |
|---|---|
| `orig_lon` / `orig_lat` | **最初に動かしたときだけ**記録される、登録時の位置 |
| `orig_note` | そのときの `loc_accuracy`（「小班の代表点」など） |

`POST /api/tree/<id>` に `lon`/`lat` を渡すと、
`orig_lon` が空のときだけ現在値を退避してから更新する。
つまり **何度動かしても「いちばん最初の位置」に戻せる**。

`POST /api/tree/<id>/reset_position` で復元し、`orig_*` を空に戻す。

画面側は `S.move` が調整中の状態を持ち、
`onMapClick` が `S.move` を最優先で見るので、
調整中は「木を登録」「距離」より位置指定が優先される。
確定は `commitMove()`、中断は `endMove()`。

## 15. 座標の読み取り（parseCoord / coordFrom）

現場の道具（ジオグラフィカ、地理院地図、GPS機）が出す書き方はばらばらなので、
`app/app.js` の `parseCoord()` で正規化してから使う。

```
入力文字列
  ↓ 全角→半角、北緯/南緯/東経/西経→NSEW、°′″度分秒→空白
  ↓ 「X=… Y=…」があれば平面直角座標として確定（X=北, Y=東）
  ↓ 数字と NSEW を出現順にトークン化
  ↓ 半球記号の位置でふたつのまとまりに割る
  ↓   記号が前（N42… E140…）／後ろ（42…N 140…E）の両方に対応
  ↓ 各まとまりの数字が 1個→度／2個→度分／3個→度分秒
  ↓ NS が付いた側を緯度、EW が付いた側を経度に割り当てる
{lat, lon} または {xy:[東, 北]}
```

- 半球記号が無く両方 180 以下なら緯度経度、そうでなければ平面直角座標とみなす。
- 平面直角座標は逆変換を持たないので、`xyToLatLon()` が `/api/locate` を
  最大8回呼んで 2cm 以内に寄せる（ニュートン法ではなく単純な反復）。
- 並びが逆に書かれていることがあるので、`coordFrom()` は日本式（X=北, Y=東）で
  読んでみて森町から外れたら入れ替えて再計算する（`NEAR_MORI`）。
- **表示も日本式に直してある。** `fmt.xy(east, north)` が `X <north>  Y <east>` を
  返す。内部（`geo.py`、DBの `trees.x`/`trees.y`）は GIS 式に x=東, y=北 のままなので、
  混同しないこと。

自動テストは無いので、直したときはブラウザのコンソールで

```js
["42.105986, 140.683474", "N42°06'21.5\" E140°41'00.5\"",
 "N42°06.358' E140°41.008'", "北緯42度6分21.5秒 東経140度41分0.5秒",
 "X=-209542.46 Y=37167.87"].map(parseCoord)
```

を通して確かめる。

### 度分秒で貼ると数メートルずれる

GPS機の度分秒表示は 0.1秒（緯度で約3.1m、経度で約2.3m）までしか出ない。
度分表示は 0.001分（約1.9m）。**貼り付けた時点で数メートルの丸め誤差が乗る。**
画面のヒントにもそう書いてあるが、問い合わせが来たらまずここを確認すること。

## 16. 距離をはかる

`S.mode === 'measure'` のとき `onMapClick` が `measureAdd()` を呼ぶだけの簡単なもの。
`S.layers.tools` に破線のポリラインと点を置き、2点目以降の点に
「合計距離／区間距離／方角」の常時表示ツールチップを付ける。

木のマーカーは `bubblingMouseEvents: false` なので、モード中はマーカーの
クリックハンドラ `hitTree()` が `onMapClick(ev)` に転送する。
これで **木の上をタップしても計測点になる**（詳細は開かない）。

計測中は `map.doubleClickZoom` を切り、ダブルクリックを「終わり」に使う。
ツールチップの DOM は Leaflet のフェードアウト（200ms）で遅れて消えるので、
消えたかどうかを即座に確認すると残って見える。

## 17. 画面ファイルのキャッシュ

`/app/` 以下は `Cache-Control: no-store` で返す（`server.py` の `do_GET`）。
`app.js` を直したのに画面が変わらない、という事故を防ぐため。
タイル・背景地図・写真は中身が変わらないので `max-age=86400`。

`do_DELETE` は中身（Content-Length）があれば読み捨てる。
読まずに応答すると keep-alive の接続が壊れ、
次のリクエストが `Unsupported method` になる。
